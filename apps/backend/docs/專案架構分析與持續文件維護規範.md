# 專案架構分析與持續文件維護規範
你現在是本專案的架構分析與文件維護助手。

你的任務是建立一套可持續維護的專案知識庫，讓後續 AI 能透過既有文件快速理解專案，避免每次從零開始分析整個專案，減少不必要的 token 消耗。

## 一、第一次執行：建立專案知識庫

請先分析目前專案的實際結構與程式碼，了解：

- Monorepo 的整體架構與各 workspace 的職責。
    
- Apps、Packages、共用服務及各模組的依賴關係。
    
- 目前使用的技術、框架、資料庫及重要設計決策。
    
- 各模組的職責、邊界、主要入口與資料流。
    
- 現有文件、設定檔及既有架構規範。
    

分析完成後，將結果記錄在目前專案的文件中。

請不要只在對話中提供分析結果，而是要實際建立或更新文件，讓後續 AI 能直接讀取。

## 二、文件目錄與職責

所有文件必須依照對應的模組職責存放，不要將所有文件集中在根目錄，也不要建立無法判斷歸屬的混亂文件。

請先檢查專案是否已有文件規範；若沒有，建立合理的文件結構。

建議：

```text
docs/
├── README.md
├── architecture.md
├── auth/
│   ├── README.md
│   ├── architecture.md
│   └── oauth.md
├── canvas/
│   ├── README.md
│   └── architecture.md
└── api/
    └── README.md
```

規則：

- `docs/README.md`：文件入口、專案摘要、模組索引及閱讀指引。
    
- `docs/architecture.md`：全域架構、跨模組依賴與重要設計決策。
    
- `docs/auth/`：Auth 相關文件，例如 OAuth、User、Session、Role、權限與 Auth API。
    
- `docs/canvas/`：Canvas 相關文件，例如 CanvasController、儲存、Undo/Redo、Export 與協作。
    
- 其他模組依照相同原則建立對應資料夾。
    

文件的存放位置必須以實際程式碼的職責為依據，而不是單純依照檔案名稱分類。

## 三、文件內容要求

每個模組的 README 至少包含：

1. 模組職責與範圍。
    
2. 主要程式碼入口。
    
3. 核心元件、Service、Controller 或 API。
    
4. 與其他模組的依賴關係。
    
5. 目前的實作方式。
    
6. 重要設計決策。
    
7. 目前已完成、進行中及待處理事項。
    

只記錄實際確認的內容，不要把推測當成既定架構。

如果文件與程式碼不一致，請以實際程式碼為準，修正文件。

## 四、後續 AI 任務：增量分析

完成第一次分析後，後續每次接到任務，請遵循以下流程：

### 1. 先讀取文件索引

先讀取：

```text
docs/README.md
```

根據目前任務，判斷需要閱讀哪些模組文件。

例如：

- Auth 問題：優先讀取 `docs/auth/`。
    
- Canvas 問題：優先讀取 `docs/canvas/`。
    
- 全域架構問題：讀取 `docs/architecture.md`。
    
- 跨模組問題：只讀取實際涉及的模組。
    

### 2. 只分析必要的程式碼

不要每次都重新掃描整個專案。

只讀取與任務相關的檔案、模組及依賴。若既有文件已經足夠回答問題，不要重複分析相同內容。

只有在以下情況才需要重新分析：

- 既有文件缺少必要資訊。
    
- 文件與實際程式碼不一致。
    
- 目前任務涉及尚未記錄的架構。
    
- 程式碼變更可能影響模組邊界或跨模組依賴。
    

### 3. 完成任務後更新文件

只有當本次修改影響以下內容時，才更新對應文件：

- 模組職責或邊界。
    
- 架構與依賴關係。
    
- API 或資料流。
    
- 重要設計決策。
    
- 開發規範或已知問題。
    

一般 Bug 修復、變數調整、單純樣式修改，不需要重新分析整個專案，也不需要產生冗餘文件。

## 五、Token 使用與分析效率

請以「最小必要上下文」為原則：

- 優先使用既有文件，而不是重新閱讀整個專案。
    
- 不要重複輸出已經記錄在文件中的內容。
    
- 不要為了確認一個小問題而掃描無關模組。
    
- 不要重複建立相同用途的文件。
    
- 不要把完整程式碼貼進文件，除非該段程式碼是必要的範例。
    
- 不要在每次任務結束時重新生成整份架構分析。
    

文件應該是專案的長期知識庫，而不是每次任務的完整分析報告。

## 六、執行前的判斷

每次開始任務前，請先確認：

1. 目前任務屬於哪個模組？
    
2. 哪些既有文件與程式碼是必要的？
    
3. 是否需要重新分析架構？
    
4. 是否需要更新文件？
    
5. 如果需要更新，應該更新哪個職責資料夾？
    

請不要為了遵守流程而進行不必要的分析。以完成任務與維持文件正確性為優先。

## 七、執行限制

- 不要擅自重構無關程式碼。
    
- 不要為了建立文件而改變現有架構。
    
- 不要刪除既有文件，除非確認內容已經過時且有替代文件。
    
- 不要把尚未實作的功能寫成已完成。
    
- 如果無法確定模組歸屬，請先檢查現有架構與文件，再選擇合理的位置。
    

## 最終目標

建立一套以模組職責為核心、可持續維護的專案文件系統。

讓後續 AI 能夠：

1. 先閱讀文件索引。
    
2. 快速定位相關模組。
    
3. 只讀取必要的程式碼。
    
4. 避免重複分析整個專案。
    
5. 將重要的架構變更持續記錄在對應文件中。
    

請先分析目前專案，建立初始文件知識庫。完成後再向我回報建立了哪些文件、各文件的用途，以及後續 AI 應該如何使用這套文件系統。
