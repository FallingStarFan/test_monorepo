# 2. 架構設計原則

本專案採取：

> **簡單、可維護、低耦合、避免過度設計**

主要原則：

1. 優先使用現有架構。
    
2. 優先修改現有程式，而不是重新建立一套架構。
    
3. 避免沒有實際需求的 abstraction。
    
4. 第三方服務應適當隔離。
    
5. API Contract 必須穩定。
    
6. 前後端資料結構需要保持一致。
    
7. 重要架構決策需要文件化。

# 8. Prisma / Database

Database 存取統一透過：

```text

```

Service 不應自行建立 Prisma Client。

Database Schema 修改時必須考慮：

- Migration
    
- Existing data
    
- API compatibility
    
- Frontend compatibility
    
- Authentication
    
- Authorization
    

Database Schema 的修改不得只考慮目前 API。

## 8.1 Public Service Auth 角色模型

`auth.User` 不再使用單一 `UserRole` enum 欄位。角色以 `App`、`Role` 與
`UserRole` 關聯表表示，讓同一位使用者可在不同 App 擁有多個角色。

- `App` 擁有多個 `Role`，同一 App 內的 role name 不可重複。
- `UserRole` 以 `userId + roleId` 作為複合主鍵，避免重複授權。
- Users API 使用 `roleIds: string[]` 指派角色；查詢結果會包含每筆授權及其
  關聯的 Role 資訊。
- 更新 `roleIds` 時會以傳入陣列完整取代既有角色；未傳入則不變更角色。

## 8.2 Public Service 細粒度權限模型

角色只回答「使用者屬於哪個 App 的哪個角色」，無法回答「這個角色能做哪些操作」，
因此在 `auth` schema 另外加入：

- `Permission`：權限碼清單（`code` 唯一），代表一個可被檢查的操作。
- `RolePermission`：`Role` 與 `Permission` 的多對多關聯，複合主鍵
  `roleId + permissionId`，`onDelete: Cascade`。

兩者與 `Role` 同屬 `auth` schema，原因是每個請求都要一次查完
「使用者 → 角色 → 權限碼」；若拆到不同 schema，Prisma 無法在同一組關聯查詢
完成，會被迫拆成兩次查詢再自行組合。

執行期檢查由 `permission` 模組負責：

- `AuthenticatedGuard`：解析 cookie 或 Bearer token，取得 `currentUserId`。
- `PermissionGuard`：檢查順序固定為 401 → 403 `NO_APP_ROLE` →
  403 `PERMISSION_DENIED`，讓前端能分辨「未登入」「不屬於這個 App」
  「屬於這個 App 但沒有這個操作權限」。
- `@RequireRole` / `@RequirePermission`：Controller 以 decorator 宣告需求。

錯誤碼定義在 `@test/shared` 的 `AUTH_ERROR_CODES`：

| 情境 | Status | code |
|---|---:|---|
| 未登入或 Token 無效 | 401 | — |
| 已登入，但在目標 App 沒有任何角色 | 403 | `NO_APP_ROLE` |
| 有角色，但角色缺少所需權限碼 | 403 | `PERMISSION_DENIED` |

管理 API（`/admin/*`）只允許 `public-service` 的 `ADMIN` 角色執行，且必須同時
具備對應權限碼；兩項條件是「且」的關係。既有未註冊的 `App` / `Role` controller
不因為本次新增而被啟用，避免產生未受保護的管理端點。

# 9. Authentication / Authorization

Authentication 與 Authorization 必須分開理解。

Authentication：

> 確認使用者是誰。

Authorization：

> 確認使用者是否有權限執行某個操作。

API 若需要登入，必須明確確認 Authentication。

API 若有角色或權限要求，必須明確確認 Authorization。

相關 Token / Session / OAuth 邏輯應保持集中管理，不應散落於各 Controller。

- Param
    
- Query
    
- Header
    

### Response

- 成功 Response
    
- Error Response
    
- Status Code
    

### Authentication
