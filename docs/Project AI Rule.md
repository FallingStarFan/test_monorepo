# Project AI Rule

請遵循以下規則管理、分析與維護本專案。

## 1. 專案文件優先

開始任何開發、分析或修改任務前，請先確認目前專案中是否存在 AI 指引文件、專案文件索引及相關模組文件。

優先閱讀：

1. AI 指引文件，例如 `AGENTS.md`
    
2. 專案文件索引，例如 `docs/README.md`
    
3. 與目前任務直接相關的模組文件
    
4. 必要時才閱讀相關程式碼

若任務涉及特定框架、套件或錯誤訊息，也必須先查閱 `docs/已知錯誤/` 中相符的紀錄。
    

不要在沒有必要的情況下重新掃描整個專案。

---

## 2. 使用現有文件建立專案上下文

請先閱讀目前專案中指定的、現有的 `.md` 專案文件，理解：

- 專案整體架構
    
- Monorepo 結構
    
- 模組職責
    
- 模組邊界
    
- 模組之間的依賴關係
    
- 技術選型
    
- API 與資料流
    
- 資料庫設計
    
- 重要設計決策
    
- 開發規範
    
- 已知限制與待處理事項
    

文件數量不固定。

不要假設專案只有三份文件，也不要限制只能參考特定數量的文件。

應根據目前專案實際存在的文件與文件索引，判斷哪些文件與當前任務相關。

---

## 3. 文件作為長期專案知識庫

專案文件不是單次分析報告，而是提供給後續 AI 使用的長期知識庫。

第一次分析專案時，應將重要且可長期使用的分析結果記錄到對應的 `.md` 文件。

後續 AI 應優先使用既有文件理解專案，而不是每次重新從程式碼開始分析。

如果文件已經包含所需資訊，不要重複分析或重新產生相同內容。

---

## 4. 文件依照職責分類

文件必須依照實際模組職責存放。

例如：

```text
docs/
├── README.md
├── architecture.md
├── auth/
│   ├── README.md
│   ├── architecture.md
│   └── oauth.md
├── canvas/
│   ├── README.md
│   └── architecture.md
└── api/
    └── README.md
```

例如：

- Auth 相關文件 → `docs/auth/`
    
- Canvas 相關文件 → `docs/canvas/`
    
- API 相關文件 → `docs/api/`
    
- 全域架構 → `docs/architecture.md`
    
- 文件入口與索引 → `docs/README.md`
    

不要將不同職責的文件全部放在同一個資料夾。

如果文件涉及多個模組，且屬於跨模組架構或全域規範，才放在全域文件。

---

## 5. 文件格式

專案架構、模組說明、設計決策、開發規範與 AI 指引，優先使用 Markdown (`.md`)。

Markdown 文件應：

- 結構清楚
    
- 使用標題分層
    
- 避免不必要的大量文字
    
- 避免重複描述
    
- 只記錄實際確認的資訊
    
- 保持內容容易被 AI 定位與理解
    

不要將完整程式碼大量複製到文件中。

只在必要時提供少量程式碼範例。

---

## 6. 建立文件索引

應維持一個主要文件入口，例如：

```text
docs/README.md
```

文件索引至少應能讓 AI 快速知道：

- 專案有哪些主要模組
    
- 每個模組的職責
    
- 對應文件位置
    
- 哪些文件是全域文件
    
- 哪些文件屬於特定模組
    

AI 接到任務時，應先透過文件索引定位需要閱讀的文件。

---

## 7. 最小必要上下文

後續執行任務時，遵循「最小必要上下文」原則。

例如目前任務是 Auth OAuth：

優先閱讀：

```text
AGENTS.md
docs/README.md
docs/auth/README.md
docs/auth/oauth.md
相關 Auth 程式碼
```

不要因為處理 Auth 問題而重新閱讀：

```text
docs/canvas/
docs/menu/
docs/booking/
其他無關模組
```

除非目前任務確實涉及這些模組。

目標是減少：

- 不必要的檔案讀取
    
- 重複分析
    
- Context 使用量
    
- Token 消耗
    

---

## 8. 什麼情況需要重新分析

只有在以下情況才重新分析相關部分：

- 文件不存在
    
- 文件資訊不足
    
- 文件與目前程式碼不一致
    
- 架構已經發生變更
    
- 任務涉及尚未記錄的模組
    
- 任務涉及新的依賴關係
    
- 無法從既有文件判斷正確的實作方式
    

即使需要重新分析，也只分析與目前問題相關的範圍。

不要因為一份文件過時，就重新分析整個專案。

---

## 9. 文件同步

當修改程式碼後，如果變更影響：

- 模組職責
    
- 架構
    
- API
    
- 資料流
    
- 資料庫設計
    
- 模組依賴
    
- 重要設計決策
    
- 開發規範
    

請同步更新對應的 `.md` 文件。

一般以下修改不需要更新架構文件：

- 一般 Bug 修復
    
- 變數命名
    
- 小型重構
    
- 單純樣式修改
    
- 不影響架構的內部實作修改
    

不要每次任務完成後重新產生完整專案分析。

只更新受到實際影響的文件。

### 9.1 AI 修改紀錄（必須）

每次 AI 對專案檔案做出實際修改後，必須在 `docs/AI修改紀錄/` 新增一份紀錄；
僅分析、回答問題或未寫入任何檔案時不需要新增。

紀錄檔名使用 `YYYY-MM-DD-HHmm-簡短主題.md`，內容保持精簡且只記錄：

- 任務與修改原因。
- 新增、修改或刪除的檔案。
- 對 API、資料庫、設定或相容性的影響；沒有則寫「無」。
- 實際執行的驗證與結果；未執行必須寫明原因。

此紀錄用於追蹤 AI 工作，不取代架構文件、API 測試文件或 Git 紀錄。若修改影響
架構或 API，仍須同步更新各自的正式文件。

### 9.2 低 Token 工作流程

為以更少 token 完成同一任務，依序執行：

1. 先讀取文件索引與本任務直接相關的規則／模組文件。
2. 用檔名、`rg` 搜尋與精確區段讀取定位程式碼，不完整掃描無關目錄或 generated code。
3. 已有文件足以回答時不重複分析；只有文件缺漏或與程式碼不一致時才增量補充。
4. 測試以受影響範圍為主，成功後停止擴大檢查；完整測試僅在變更面較廣時執行。
5. 完成後以精簡修改紀錄保存可重用結論，讓後續 AI 先讀紀錄再決定是否需要讀程式碼。

---

## 10. 文件與程式碼不一致時

如果既有文件與實際程式碼不一致：

1. 先確認目前程式碼的實際狀態。
    
2. 判斷文件是否已過時。
    
3. 修正對應文件。
    
4. 不要在新的文件中重複建立另一份相同資訊。
    

以目前實際程式碼與已確認的架構為準。

不要把推測內容寫成既定架構。

---

## 11. 不修改無關內容

執行任務時：

- 不要為了建立文件而修改無關程式碼。
    
- 不要擅自重構無關模組。
    
- 不要建立重複用途的文件。
    
- 不要刪除仍然有效的文件。
    
- 不要因為文件整理而改變目前專案架構。
    

所有修改都應與目前任務直接相關。

---

## 12. 跨 Chat 的使用方式

這套規則必須設計成可以跨不同 Chat、不同 AI Coding Agent 使用。

不要依賴目前對話中的上下文。

後續任何 AI 接手專案時，都應該能透過：

```text
AI Rule
↓
文件索引
↓
相關模組文件
↓
必要程式碼
```

快速建立目前任務所需的上下文。

專案文件才是跨 Chat 的主要長期上下文來源。

---

## 13. 最終目標

建立一套：

- 可持續維護
    
- 模組化
    
- 可跨 Chat 使用
    
- 可跨 AI Agent 使用
    
- 低重複分析
    
- 低 Context 消耗
    
- 容易人工閱讀
    
- 容易 AI 定位資訊
    

的專案知識庫。

核心原則：

> **先讀文件，後讀程式碼；先讀相關範圍，不讀整個專案；已有資訊不重複分析；架構變更才更新文件。**
